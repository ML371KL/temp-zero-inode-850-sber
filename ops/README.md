# Эксплуатация «Сбер 850»

Конвейер модели справедливой стоимости акции Сбербанка на общем сервере панелей
владельца: сбор источников, дозор релизов РСБУ и МСФО, нау-каст, сборка выпуска
`sber-v1`, публикация в публичный репозиторий данных, сверка через боевую дверь
`https://tzi-850-sber.pages.dev/api/model`. Схема — Ленты (в бою с 30.09.2026),
каркас — панели Магнита 850oa; отличия названы по месту.

Здесь — всё, что нужно для работы с конвейером, без инфраструктурных подробностей
сервера (адрес, имена ключей, доступы): они в справочнике владельца вне
репозитория. Репозиторий публичный, правило гигиены держит
`tests/test_public_hygiene.py`.

## 2. Канал данных

```
сборка (python -m model.build_release) → $BANK_STATE_DIR/release/latest.json
  → ops/publish.py: клон ветки release, releases/<sha256>.json + latest.json + history.json (+ journal.json) одним коммитом, push
  → GitHub Pages репозитория данных (сборка pages-build-deployment, обычно 1–3 минуты)
  → functions/api/model.js: Pages (минутная метка, cacheTtl 60) → raw (запасной) → копия края
  → браузер и сверка ops/publish.py --verify
```

- **Ветка только дописывается.** `releases/<sha256>.json` пишется один раз и не
  трогается никогда (прореживания нет); `latest.json` — указатель, `history.json` —
  строка на каждую публикацию и откат (PAYLOAD §4), `journal.json` — полный журнал
  прогнозов. Правило репозитория данных — без удаления ветки и без перезаписи
  истории; push — без силы.
- **Выпуски и журнал пишутся компактно** — без отступов, разделители `,` и `:`
  (выпуск на треть меньше, чем с отступами). **Сторож объёма:** после публикации
  `publish.py` меряет дерево ветки (файлы клона без `.git` — то, что раздаёт сайт
  GitHub Pages) и с порога `ops/budgets.json` → `data_branch_alert_mb` (700 МБ при
  пределе сайта 1 ГБ) отвечает кодом 3: выпуск на витрине, такт кончается
  «ТРЕВОГА (код 8)» со строкой «ПУБЛИКАЦИЯ: дерево ветки release — … МБ». Рост —
  раздел 9.
- **Хэш** `meta.payload_sha256` — по правилам PAYLOAD §0.4 (вне хэша: моменты
  сборки и публикации, ссылки на прошлые выпуски, размер, `live.fetched_at`, ссылки
  журнала на выпуски, блоки `changes` и `valuation_history`).
- **Повтор без дублей.** Выпуск с тем же хэшем, что уже в указателе, повторно не
  публикуется: ни коммита выпуска, ни строки истории (журнал обновится, если
  изменился); сверка получает `published_at` того, что уже в указателе. Быстрая
  сборка (`meta.fast: true`) не публикуется никогда.
- **`meta.published_at`** — момент публикации (UTC, ISO, секунды), вне хэша;
  вписывается при каждой публикации и откате. Из него дверь ставит
  `Last-Modified` (по нему живёт сторож) и сильный `ETag` `"<sha12>.<секунды>"`.
- **Коммит — только при разнице**; push — три попытки с растущей паузой, каждая с
  чистого клона; `gc.autoDetach=false` (systemd убил бы фоновый `git gc` и оставил
  `*.lock`). Автор коммитов — `SBER_GIT_NAME`/`SBER_GIT_EMAIL`, только
  noreply-адрес GitHub из `.github/commit-emails.allow` (сверяется со списком:
  чужой noreply и отсутствие списка — отказ, код 1).
- **Охрана каталога клона** — до любой разрушающей команды: каталог клона
  (`BANK_DATA_REPO_DIR`) не совпадает с каталогом состояния или кода и не лежит
  выше них; непустой каталог без `.git` не удаляется; каталог с `.git` обязан быть
  клоном данных этой панели — есть `refs/remotes/origin/release`, и origin
  указывает на тот же репозиторий, что `SBER_RELEASE_REMOTE` (сменить можно
  ssh-алиас, но не репозиторий: клон данных соседней панели не трогается). Иначе —
  «ПУБЛИКАЦИЯ: каталог клона данных …» или «ПУБЛИКАЦИЯ: в каталоге … клон другого
  репозитория данных», код 1, и ни один файл не тронут: опечатка в переменной
  иначе стёрла бы журнал прогнозов и невосполнимый архив — молча и на каждом такте.
- **Git без хуков:** каждая команда git публикации идёт с
  `core.hooksPath=/dev/null` и `core.fsmonitor=false` — хук или монитор файлов из
  клона данных не исполнится в такте, у которого есть ключ записи. Это наименьшие
  права, а не граница доверия: `.git/config` клона пишет тот же пользователь.
- **Сверка** читает дверь, как браузер (свой ASCII User-Agent: без него дверь
  отвечает 403), до совпадения `payload_sha256` И `published_at`. Окно —
  `SBER_VERIFY_TIMEOUT` (600 с), пауза — `SBER_VERIFY_PAUSE` (30 с). Итоги:
  - совпало, `x-data-source: pages` — строка журнала «СВЕРКА: выпуск <sha12> ·
    <момент> — пройдена с попытки N, Last-Modified …», `release.commit` = коммит
    кода выпуска, отметка `release.pushed` снимается, код 0. По этой строке и по
    `release.commit` принимают установку и каждый выпуск (раздел 5, шаг 11);
  - совпало через `raw` или `edge-cache` — выпуск засчитан, но GitHub Pages не отдаёт ветку: код 3 (тревога);
  - не дождались — код 3, `release.pushed` остаётся, `release.commit` не пишется; сверку дожимает пересборка (одна попытка раз в 15 минут).
- **Клон перед сборкой** (`ops/publish.py --sync`): сборка берёт прошлый выпуск
  (`changes`, защита заголовка) и историю оценки из клона; отказ обновления — не
  провал, строка «ВНИМАНИЕ».

## 3. Такты

| Юнит | Когда (UTC) | Что делает |
|---|---|---|
| `sber850-collect` | каждый день 04:50 (±5 мин), `Persistent` | обновление кода → зависимости → сбор двумя командами (`indicators.collect collect --only tinvest` с токеном, затем `--skip tinvest`: даты и формы ЦБ, ISS, ЦБ, новости, дозор, реестр дивидендов, ротация архива); отказал невосполнимый источник — повтор сбора внутри такта (до 3 попыток с паузой 3 мин) → по понедельникам тесты такта «в будущем» (+60 дней) → объём → здоровье (тревога) |
| `sber850-release-watch` | будни 06:45–09:55 каждые 10 минут (09:45–12:55 МСК) | тихая проверка окна (календарь индикаторов, отложенное) → обновление кода → зависимости → дозор (`indicators.collect release-watch`: новость + статический PDF, приём при двух источниках) → что принято (`ops/tact.py news`) → при новом: нау-каст → тесты такта → клон данных → сборка → публикация → сверка |
| `sber850-daily` | будни 18:10 (±5 мин), `Persistent` | обновление кода → зависимости → сбор рядов и цен (`daily-indicators`, сборщик T-Invest — отдельной командой с токеном) → нау-каст → здоровье (напоминание) → тесты такта → клон данных → сборка → публикация → сверка → объём |
| `sber850-rebuild` | `*:12,27,42,57` | тихая проверка: дожим сверки прошлого такта; если код в `CODE_DIRS` (`model`, `indicators`, `ops`, `data/assumptions`, `data/facts`, `data/indicators`, `data/checks`, `requirements.txt`, без `*.md`) изменился с `release.commit` — тесты такта → клон данных → сборка → публикация → сверка, без сбора |

- **Обновление кода** — `git fetch` + `reset --hard origin/main` и `exec` нового
  `run.sh` один раз за такт (иначе bash доигрывал бы прежний файл). GitHub не
  читается — такт идёт на текущем коде (утренний срез дороже свежести кода).
- **Зависимости** — по отметке `sha256(requirements.txt)` в venv, каждый такт до
  работы; отметка пишется только после удачного `pip install`, неудача — провал.
  Транзитивные пакеты закреплены в `requirements.txt` теми же версиями.
- **Env-файл читает `run.sh`, а не systemd.** Юнит передаёт только путь
  (`Environment=ENV_FILE=…`; строки `EnvironmentFile` в юнитах нет). `run.sh`
  читает файл (`set -a; . "$ENV_FILE"; set +a`) и сразу снимает `TINVEST_TOKEN` из
  окружения такта в неэкспортируемую переменную шелла.
- **Токен T-Invest — только сборщику T-Invest.** Токен передаётся одной команде —
  `indicators.collect <режим> --only tinvest`; остальные сборщики (`--skip tinvest`:
  чужой HTML и PDF), нау-каст, `pip`, тесты, сборка, публикация и мост тревог идут
  без токена (тест такта `tests/test_ops_run_sh.py`). Это гигиена окружения, а не
  граница доверия: env-файл читаем пользователем `dash`.
- **Тесты такта** — белый список по метке `tact` (`pytest.ini`), выражение
  `TACT_TESTS` в `run.sh`; ноль выбранных — провал. Быстрые тесты такта есть у
  каждого потока — ядро, книга, факты, индикаторы, витрина, контрольная модель,
  перезаякоривание, эксплуатация (сверяет `tests/test_ops_tact_suite.py`). Весь набор — не дольше
  3 минут на сервере (`ops/budgets.json` → `tact_tests_target`; сверяется замером —
  итоговая строка pytest «N passed in T s» в шаге «тесты такта» журнала такта,
  раздел 9). Шаг CI «Тесты такта — замер времени»
  печатает `--durations` и краснеет после 300 с (`tact_tests_ci_ceiling`: раннер с
  двумя ядрами медленнее сервера), а время дольше цели сервера печатает
  предупреждением. Сторож `tests/conftest.py` не даёт полному выпуску пробраться
  в такт.
- **Сроки данных в такт не входят.** Тест срока (метка `deadline`: объяснение
  сработавшего гейта действует на сегодня) выражение `TACT_TESTS` исключает; он
  идёт в CI и в ручном прогоне. Срок проверяет сама сборка (раздел 4): истёкшее
  объяснение сработавшего гейта — отказ, истекающее и истёкший срок документа
  эмитента — плашки выпуска. Поэтому набор сервера обязан быть зелёным на любой
  будущей дате: утренний такт по понедельникам гоняет его с «сегодня» + 60 дней,
  CI 1-го числа каждого месяца — весь набор без тестов сроков с + 180 дней.
  Красное «будущее» (тревога «тесты такта с FAKE_TODAY=… падают») — тест,
  привязанный к дате: это дефект теста, а не будильник данных.
- **Замок** один; утренний и суточный такты ждут его до `LOCK_WAIT_SECONDS` (=
  наибольший потолок пересборки и дозора), пересборка и дозор на занятом замке
  молча выходят с 0 — следующая проверка через 10–15 минут.
- **Дозор без потерь.** Принятый месяц РСБУ или новый кандидат МСФО ложится в
  `release_watch.pending` и снимается только после публикации: упавшая сборка не
  теряет релиз — его соберёт следующий такт дозора или суточный.

## 4. Коды и тревоги

**В штатном состоянии каждый такт кончается кодом 0.**

| Код юнита | Смысл | Повтор systemd |
|---|---|---|
| 0 | прошло (последняя строка журнала — «готово: …») | — |
| 1 | ПРОВАЛ шага, выпуска нет (в журнале «ПРОВАЛ на шаге «…» (код N). На витрине остаётся прежний выпуск.») | `daily`, `collect` — через 3 мин, не больше 3 стартов за окно (≈ 7 ч), дальше юнит стоит до следующего таймера; дозор и пересборка — следующей проверкой |
| 8 | ТРЕВОГА: работа выполнена, выпуск (если такт его делает) на витрине; последняя строка — «ТРЕВОГА (код 8): <причины>» | нет — ни у одного такта (`RestartPreventExitStatus=8`): повтор тревогу не снимет |
| 64 | неверный режим или проба тревоги с источником не из такта | нет |
| 75 | замок держит другой такт дольше `LOCK_WAIT_SECONDS` | да, в том же окне |
| 78 | нет env-файла, в нём нет `SBER_REPO_DIR`/`BANK_STATE_DIR` или каталог кода `SBER_REPO_DIR` — не клон git (в нём нет `.git`: такт не отдаёт `git fetch` и `git reset --hard` репозиторию выше) | нет |

**Окно перезапуска.** systemd отсчитывает `StartLimitIntervalSec` от первого старта
и окно не двигает, поэтому оно обязано вмещать три самых долгих прогона с паузами:
`StartLimitIntervalSec` = 3 × (`RuntimeMaxSec` + `RestartSec` + 90 с на
`ExecStopPost`), считается из `ops/budgets.json` (`restart`), равенство сверяет
`tests/test_ops_units.py`. Стойкий отказ (гейт, защита заголовка, отозванный ключ)
даёт три прогона и стоп: `systemctl status` покажет `start-limit-hit`, следующий
запуск — по таймеру; раньше — `sudo systemctl reset-failed sber850-<такт>.service`.

**Три исхода** (docs/INTERFACES.md §6). Отказ — выпуска нет, на витрине прежний.
Тревога — то, что требует человека и что повтор не снимет; повтор — только там,
где он спасает данные. Плашка — срок, о котором достаточно знать заранее: она
печатается в выпуске и на витрине, такт о ней не тревожит.

**Сборка выпуска** (`python -m model.build_release`):

| Код сборки | Что | Такт |
|---|---|---|
| 0 | выпуск собран — в том числе с плашками: объяснение сработавшего гейта истекает в ближайшие 30 дней (флаг `explanation_expiring`: гейт и дата); срок документа эмитента истёк (флаг `policy_expired`: срок дивидендной политики — «действует прежняя до новой») | публикация, код такта 0 |
| 3 | выпуск собран, но требует человека: деградировал живой вход оценки (цена не принята, запись реестра не принята, кривая или ключевая не приняты) или источник, уже получивший код 3 у сборщиков; флаг `dividend_register` — нет записи реестра объявленных дивидендов за год к концу квартала ГОСА; выпуск от 400 000 байт | публикация, в конце — «ТРЕВОГА (код 8): сборка подняла тревогу …» |
| 1 | выпуск не собран: нарушен инвариант или контракт; сработавший гейт без действующего объяснения — нет записи, срок истёк или **масса вне коридора ожидания** (MODEL §14.2); защита заголовка; нет цены главного тикера | «ПРОВАЛ на шаге «сборка выпуска»», на витрине прежний выпуск |

Масса гейта вне коридора — отказ, а не тревога: объяснение с другой массой уже
не объясняет то, что сработало. Лечится правкой `expected_mass`/`expected_mass_range`
в `data/assumptions/gate_explanations.yaml` (с текстом, почему) или причины.
Истёкшее объяснение сработавшего гейта лечится новой записью объяснения со сроком
или перезаякориванием (docs/MANUAL.md §10.4, §10.9); плашка `explanation_expiring`
появляется за 30 дней до этого.

**Сбор источников** (`python -m indicators.collect <режим>`):

- **Невосполнимый источник** (винтажи форм ЦБ, снимки T-Invest, новости и PDF дня
  релиза) отказал: сборщики отвечают кодом 3 и ставят в `collector_report.json`
  `retry: true`. Утренний такт в этом и только в этом случае повторяет сбор сам,
  внутри прогона, — всего до 3 попыток с паузой 3 мин (`ops/budgets.json` →
  `collect_retry`); не добрал — «ТРЕВОГА (код 8): невосполнимый источник не собран
  (попыток: 3 …)». Суточный такт и дозор сбор не повторяют.
- **Источник без токена** — тревога без повтора: повтор токена не добавит.
- **Восполнимый источник**, питающий только плитки и наблюдения, деградировал: до
  третьего такта подряд — код 0, строка «деградация (такт k из 3)» в журнале и
  причина в выпуске (`live.degraded`, плитка); с третьего — тревога «сбор требует
  внимания …». Счётчик считается раз за день и сбрасывается первым удачным
  сбором. **Такты со сборкой судят источники тем же счётчиком:** сборка поднимает
  тревогу только по живым входам оценки и по источникам, уже получившим код 3 у
  сборщиков, — причина моложе трёх тактов тревогой не становится.
- **Критический источник** (запасной путь цен и кривой): отказ — код 1, провал
  шага, повторяет systemd в пределах окна; его деградация — тревога сразу.
- Тревога реестра дивидендов, тяжёлый выпуск, дерево ветки данных у порога,
  несостоявшаяся сверка, красное «будущее» — тревога сразу, без повтора.

Внутри такта шаги отвечают кодом 3 «сделано, но требует внимания» (невосполнимый
источник не добран или сбор требует внимания, тревога сборки, нау-каст записан не
целиком, публикация с замечанием, сверка не дождалась выпуска, красное «будущее»);
причины копятся и уходят одним кодом 8 в конце — последняя строка «ТРЕВОГА (код 8): …».
Других кодов тревоги у такта нет. Любой другой ненулевой код шага превращается в
1. Пересборка на коммите, где она уже падала, выходит с 1 без работы: «упало»
пришло один раз.

**Что видно в журнале такта** (`journalctl -u sber850-<такт>` и
`logs/<дата>.log`): шапка «Сбер 850 · такт … · время · каталог», затем шаги
строками «── шаг ── чч:мм:ссZ» (по ним меряются потолки), строки сборщиков,
сборки и публикации («выпуск <sha12> …», «отправлено в release», «СВЕРКА: …»,
«ПУБЛИКАЦИЯ: …»), и последняя строка — «готово: …», «ТРЕВОГА (код 8): …» или
«ПРОВАЛ на шаге «…» (код N)».

Мост `dash-alert` зовётся из `ExecStopPost` всегда и шлёт смену состояния: «упало»
и «снова проходит». **Стоящая тревога держит юнит в «упало»:** новая причина при
стоящей тревоге сообщения не даст — её читают в журнале такта (последняя строка
«ТРЕВОГА (код 8): …» называет все причины прогона). Поэтому код 8 оставлен тому,
что действительно требует человека, а сроки данных ушли в плашки. Панель
регистрируется строкой у `dash-watch` (адрес двери, порог свежести по
`Last-Modified`) и веткой в `dash-alert` — по процедуре служебного репозитория
панелей. Выпуск с тем же хэшем не публикуется повторно, и `Last-Modified` не
двигается, пока не меняются цена или входы: порог сторожа — с запасом на выходные
и праздники без торгов.

**Проба доставки тревоги.** Мост `dash-alert` зовётся только из `ExecStopPost`
юнита, поэтому проба идёт через systemd — временной вставкой юнита (живёт в
`/run`, до перезагрузки): утренний такт проходит как обычно, а в конце названный
невосполнимый источник объявляется отказавшим — код 8 по боевому пути.

```bash
sudo systemctl edit --runtime sber850-collect.service
#   во вставке — три строки:
#   [Service]
#   Environment=SBER_SIMULATE_FAILURE=cbr_forms
#   Restart=no
sudo systemctl --wait start sber850-collect.service
systemctl show -p ExecMainStatus sber850-collect.service    # ExecMainStatus=8
journalctl -u sber850-collect -n 5 --no-pager                 # «ТРЕВОГА (код 8): … ПРОБА ТРЕВОГИ: источник cbr_forms объявлен отказавшим …»
sudo rm -r /run/systemd/system/sber850-collect.service.d && sudo systemctl daemon-reload
```

В Telegram обязано прийти сообщение с именем панели — оно и проверяет ветку
панели в мосте. Вставку снимать именно удалением каталога из `/run`:
`systemctl revert` снял бы и постоянные вставки. `Restart=no` — чтобы проба не
повторялась, если такт кончится провалом шага. Следующий плановый утренний такт
обязан прислать «снова проходит». Имя не из невосполнимых источников такта — код
64 без работы. Запуск `run.sh` руками (`sudo -u dash env ENV_FILE=… SBER_SIMULATE_FAILURE=…
bash ops/run.sh collect`) мост не зовёт: им проверяются только коды 8 и 64.

## 5. Установка на сервер (по шагам)

Сервер — шаблон панелей владельца: пользователь `dash` с домашним каталогом
`/srv/dash`, общие скрипты `dash-alert` и `dash-watch`. Панель занимает три места:
код `/srv/dash/repo-850-sber`, состояние `/var/lib/sber-850`, настройки
`/usr/local/etc/sber-850/env`. Команды — под служебным пользователем с `sudo`;
значения с доступами (адрес сервера, имя файла ключа, ssh-алиас, токен) — в
справочнике владельца вне репозитория, здесь они стоят в угловых скобках.

Порядок обязателен: первый выпуск в ветке → GitHub Pages → витрина → таймеры, иначе
боевой адрес отвечает 503. Что уже сделано до установки (docs/DECISIONS.md,
часть 7): оба репозитория и проект Pages созданы, deploy-ключ и env-файл с
токеном лежат на сервере, tesseract установлен. У таких шагов исполняется
проверка; команда шага безвредна и при повторе.

Помощник для команд слоя ops — под пользователем конвейера, с настройками
env-файла и **без токена T-Invest** (токен нужен только пробе источников, шаг 6):

```bash
ops850() { sudo -u dash bash -c 'set -a; . /usr/local/etc/sber-850/env; set +a; unset TINVEST_TOKEN; cd /srv/dash/repo-850-sber && exec "$@"' ops850 "$@"; }
```

1. **Код и окружение.**
   ```bash
   sudo apt-get install -y python3.12-venv tesseract-ocr tesseract-ocr-rus
   sudo -u dash git clone --single-branch --branch main \
        https://github.com/ML371KL/temp-zero-inode-850-sber.git /srv/dash/repo-850-sber
   sudo -u dash python3.12 -m venv /srv/dash/repo-850-sber/.venv
   sudo -u dash /srv/dash/repo-850-sber/.venv/bin/pip install -q -r /srv/dash/repo-850-sber/requirements.txt
   ```
   Проверка: `tesseract --list-langs | grep -x rus` печатает `rus`;
   `sudo -u dash /srv/dash/repo-850-sber/.venv/bin/python -c 'import yaml, pdfplumber, pypdfium2; print("ok")'`.
   Пакеты нужны уже пробе источников (шаг 6), до первого такта. Дальше их держит
   такт по отметке `.venv/.requirements.sha256`; отметку руками не писать — первый
   такт поставит её сам (перенаправление `>` выполнила бы оболочка без прав `dash`).
2. **Настройки.** Файл создаётся из образца, только если его ещё нет (готовый
   файл с токеном команда не трогает):
   ```bash
   sudo install -d -o root -g dash -m 750 /usr/local/etc/sber-850
   sudo test -e /usr/local/etc/sber-850/env || \
        sudo install -o root -g dash -m 640 /srv/dash/repo-850-sber/ops/env.example /usr/local/etc/sber-850/env
   sudoedit /usr/local/etc/sber-850/env
   ```
   В образце только имена — значения вписываются здесь:
   `SBER_REPO_DIR=/srv/dash/repo-850-sber`, `BANK_STATE_DIR=/var/lib/sber-850`
   (без них — код 78); `TINVEST_TOKEN` — токен T-Invest «только чтение» (секрет:
   только в этом файле), выпущенный на отдельный счёт без активов, а не на основной
   счёт владельца: токен «только чтение» открывает портфель и операции того счёта,
   на который выпущен; `SBER_RELEASE_REMOTE` — ssh-алиас deploy-ключа вида
   `<алиас>:ML371KL/temp-zero-inode-850-sber-data.git`; `SBER_GIT_NAME` и
   `SBER_GIT_EMAIL` — noreply-адрес из `.github/commit-emails.allow`;
   `SBER_PUBLIC_URL` — пусто (дверь по умолчанию) или адрес двери. Необязательные:
   `BANK_DATA_REPO_DIR` (без нужды не задавать: каталог охраняется, раздел 2), `SBER_VENV`, `SBER_PYTHON`, `SBER_VERIFY_TIMEOUT`,
   `SBER_VERIFY_PAUSE`, `SBER_PUSH_BACKOFF`, `BANK_WORKERS` (процессов полосы; до
   замера — пусто, после — число явно, раздел 9, шаг 14), `SBER_FUTURE_WEEKDAY`,
   `SBER_FUTURE_DAYS`. Имена — раздел 11.

   Проверка — печатаются только имена, значения не выводятся:
   ```bash
   sudo stat -c '%U:%G %a' /usr/local/etc/sber-850/env      # root:dash 640
   sudo -u dash bash -c 'set -a; . /usr/local/etc/sber-850/env; set +a
        for v in SBER_REPO_DIR BANK_STATE_DIR TINVEST_TOKEN SBER_RELEASE_REMOTE SBER_GIT_NAME SBER_GIT_EMAIL; do
          [ -n "${!v}" ] && echo "$v задана" || echo "$v ПУСТА"; done'
   ```
   **Кто читает файл.** Юниты systemd env-файл не читают: в них стоит только путь
   (`Environment=ENV_FILE=/usr/local/etc/sber-850/env`), строки `EnvironmentFile`
   нет — иначе токен лежал бы в окружении всего юнита, включая мост тревог. Файл
   читает `ops/run.sh`; он сразу снимает `TINVEST_TOKEN` из окружения такта и
   передаёт его одной команде — сборщику T-Invest (раздел 3). Поэтому и ручные
   команды установки идут через помощник `ops850` — без токена.
3. **Ключ записи в репозиторий данных.** Публичный репозиторий данных создаётся
   на GitHub до ключа (ветку `release` создаст шаг 5 — он ходит уже через
   ssh-алиас ключа). Отдельный deploy-ключ ed25519 в каталоге `/srv/dash/.ssh/`
   (имя файла и алиас — в справочнике владельца); если ключа ещё нет:
   ```bash
   sudo -u dash ssh-keygen -t ed25519 -N '' -C 'sber-850-data' -f /srv/dash/.ssh/<файл ключа>
   ```
   Открытая часть (`<файл ключа>.pub`) — в **репозиторий данных**: Settings →
   Deploy keys → Allow write access. В репозиторий кода ключ не добавляется
   никогда: код сервер берёт анонимно. В `/srv/dash/.ssh/config` — алиас:
   ```
   Host <алиас>
       HostName github.com
       User git
       IdentityFile /srv/dash/.ssh/<файл ключа>
       IdentitiesOnly yes
   ```
   Ключ хоста GitHub — заранее в `/srv/dash/.ssh/known_hosts`: под
   `ProtectSystem=strict` каталог только для чтения, и ssh в юните его не допишет
   (`BatchMode=yes` — будет отказ, не вопрос). Если строки ещё нет (отпечаток
   сверить с опубликованным GitHub):
   ```bash
   sudo -u dash sh -c 'ssh-keygen -F github.com -f /srv/dash/.ssh/known_hosts >/dev/null ||
        ssh-keyscan -t ed25519 github.com >> /srv/dash/.ssh/known_hosts'
   sudo -u dash ssh-keygen -lf /srv/dash/.ssh/known_hosts
   ```
   Проверка: `sudo -u dash ssh -T <алиас>` — «Hi ML371KL/temp-zero-inode-850-sber-data!
   You've successfully authenticated…» (код возврата ssh при этом 1 — так отвечает GitHub).

9. **Первый сбор и первый выпуск руками** (видно все шаги):

11. **Витрина и приёмка выпуска.** Проект Pages `tzi-850-sber` создаётся один раз
    владельцем — в панели Cloudflare или через API, производственная ветка `main`

    ```bash
    npx wrangler@4.135.0 pages project list          # в списке есть tzi-850-sber
    npx wrangler@4.135.0 pages deploy web --project-name tzi-850-sber --branch main
    curl -sI -A tzi-850-sber-check/1.0 https://tzi-850-sber.pages.dev/api/model | grep -iE '^(HTTP|x-data-source)'
    ```
    Дверь отвечает `200` и `x-data-source: pages`. Затем на сервере сверку
    дожимает пересборка — по таймеру или сразу:
    ```bash
    sudo systemctl start --wait sber850-rebuild.service; systemctl show -p ExecMainStatus sber850-rebuild.service
    journalctl -u sber850-rebuild -n 20 --no-pager | grep 'СВЕРКА: .* пройдена'
    sudo cat /var/lib/sber-850/release.commit; sudo -u dash git -C /srv/dash/repo-850-sber rev-parse HEAD
    sudo test ! -e /var/lib/sber-850/release.pushed && echo "отметка сверки снята"
    ```
    **Приёмка установки — не по коду первого такта, а по трём признакам:** в
    журнале есть строка «СВЕРКА: выпуск <sha12> · … — пройдена …»;
    `release.commit` равен коммиту кода на сервере; отметка `release.pushed`
    снята. Суточный юнит после шага 9 остаётся в «упало» до своего следующего
    прогона — он кончится кодом 0 (можно запустить сразу:
    `sudo systemctl start --wait sber850-daily.service`). Команду
    `ops/publish.py --verify` без окружения сервера не запускать: она прочла бы
    пустое состояние рабочей копии и ответила «сверять нечего» с кодом 0 — ложное
    «сверено».

    Текст экранов на первом живом выпуске — с ноутбука, тем же Node, что у
    wrangler (на выпуске из фикстуры эту проверку гоняет CI):
    ```bash
    curl -s -A tzi-850-sber-check/1.0 https://tzi-850-sber.pages.dev/api/model -o var/first-release.json
    node tests/web/web_release_text.mjs var/first-release.json | tail -n 3; echo "код ${PIPESTATUS[0]}"
    ```
    Годный итог — `"failed": []` и код 0: на шести экранах нет служебного текста
    (имён полей и методов API, рабочих пометок, дат без года). Отказ называет экран,
    правило и образец строки; правится источник строки в фактах или книге, не витрина.
12. **Таймеры**: `sudo systemctl enable --now sber850-collect.timer sber850-release-watch.timer sber850-daily.timer sber850-rebuild.timer`;
    проверка — `systemctl list-timers 'sber850-*'` (четыре строки).
13. **Сторож и мост** — регистрация панели у общего моста тревог и сторожа
    свежести по процедуре служебного репозитория панелей (раздел 4): ветка панели
    в `dash-alert`, строка у `dash-watch` с адресом двери и порогом свежести. Затем
    проба доставки тревоги через юнит (раздел 4): сообщение в Telegram с именем
    панели и «снова проходит» после следующего утреннего такта. Если следующий
    утренний такт — понедельничный и «будущее» красное, «снова проходит» не
    придёт: причина — в его журнале, это дефект теста (раздел 3).
14. **Замер времени и памяти** — после первых тактов: время шагов из журнала →
    `ops/budgets.json` (`status: measured`, `measured_on`) → потолки юнитов и
    `LOCK_WAIT_SECONDS`, окна перезапуска (раздел 9) → юниты заново (раздел 7). Шаг
    «тесты такта» — против цели `tact_tests_target` (180 с): дольше — метка `tact`
    снимается с самых долгих тестов. Тем же замером —
    число процессов полосы: `BANK_WORKERS` вписывается в env-файл ЯВНО (раздел 9);
    сюда же — время и память распознавания из шага 7.

## 6. Откат

```bash
sudo -u dash env ENV_FILE=/usr/local/etc/sber-850/env \
     bash /srv/dash/repo-850-sber/ops/run.sh rollback <sha выпуска, от 12 знаков> "причина"
```

Под тем же замком, что и такты: `latest.json` перезаписывается выпуском
`releases/<sha>.json` с НОВЫМ `published_at` (со старым сторож сразу объявил бы
панель мёртвой), в `history.json` — строка `rollback` с причиной (третий
аргумент; без него — «откат с <прежний sha12>»), затем сверка. Список выпусков —
`history.json` и `ls releases/` в
`/var/lib/sber-850/data-repo`. Ничего не удаляется; `release.commit` откат назад
не двигает. Если откатывают выпуск, чья сверка ещё не завершена (отметка
`release.pushed` висит), откат записывает в `release.commit` код этого выпуска:
иначе пересборка сочла бы код новым и за 15 минут вернула бы выпуск поверх отката.
Откат — пауза на один такт, а не состояние: ближайший выпуск (суточный
такт, дозор или пересборка на новом коммите) перепишет указатель. Если причина не
устранена — остановить таймеры:
`sudo systemctl stop sber850-daily.timer sber850-release-watch.timer sber850-rebuild.timer`.

## 9. Потолки времени и бюджеты

- **Время**: `RuntimeMaxSec` юнитов, `LOCK_WAIT_SECONDS`, окна перезапуска
  (`StartLimitIntervalSec`) и повтор сбора (`COLLECT_RETRY_*` в `run.sh`) считаются
  из `ops/budgets.json` (формулы — в поле `about`); равенство сверяет
  `tests/test_ops_units.py`. До замера там оценка (`status: estimate`): сборка
  1 200 с (цель MODEL §10 — полный выпуск на 4 процессах не дольше 15 минут),
  тесты такта 180 с, сверка до 600 с, запас ×1,5. Потолок ниже настоящего времени
  убивает такт на середине. Тесты такта: 180 с — цель сервера (`tact_tests_target`),
  она сверяется замером шага «тесты такта» в журнале первых тактов; шаг CI с тем же
  набором краснеет после 300 с (`tact_tests_ci_ceiling`) — раннер GitHub с двумя
  ядрами медленнее сервера, и его время целью сервера не служит.
- **Память и процессы полосы** (`BANK_WORKERS`): `MemoryHigh=384M`,
  `MemoryMax=512M`, `Nice=10` — ПРЕДВАРИТЕЛЬНО, по Ленте. Полоса неопределённости
  считает пулом процессов: `auto` — ядра − 1, но не больше 7; рабочий процесс
  на пике — десятки МБ (замер этапа 2 на ноутбуке — около 35 МБ), и на машине с
  8 ядрами и больше 7 рабочих вместе с главным процессом сборки подходят к
  `MemoryHigh` (дросселирование). Поэтому на сервере `BANK_WORKERS` задаётся
  **явно** после замера первых тактов: время шага «сборка выпуска» (строки
  «── шаг ── чч:мм:ссZ») и пик памяти юнита (строка systemd «… memory peak» в
  `journalctl -u sber850-daily` по окончании прогона) при 2 и 4 процессах;
  выбирается число, при котором сборка укладывается в бюджет `build`, а пик —
  ниже `MemoryHigh` с запасом; итог — в env-файл и в `ops/budgets.json`.
- **Распознавание PDF** (дозор в день релиза РСБУ): время и пик памяти — из
  дымовой проверки (раздел 5, шаг 7); время входит в шаг `watch` бюджета.
- **Диск**: сырой архив под потолком `indicators/store.py` (защищённые источники не
  ротируются).
- **Ветка данных** только дописывается. Выпуск — около 0,29 МБ компактно (с
  отступами было бы 0,43 МБ); в `.git` — ещё 70–80 КБ; клон `data-repo` растёт
  примерно на 0,36 МБ на публикацию. Сайт GitHub Pages (дерево ветки) при 260
  публикациях в год прибавляет ≈ 75 МБ в год, при 400 — ≈ 115 МБ: порог сторожа
  700 МБ наступит через 6–9 лет, предел сайта 1 ГБ — через 9–13; с ростом истории
  оценки в выпуске — раньше. Прореживания нет (решение ведущего 01.10.2026): что
  делать со старыми выпусками, решается по тревоге сторожа.
- **GitHub**: Actions и Pages публичного репозитория бесплатны; Pages из ветки —
  мягкий лимит 10 сборок в час (публикации не чаще раза в 10 минут даже в день
  релиза).

## 12. Первый push репозитория кода

Делается один раз, владельцем или ведущим (`docs/DECISIONS.md`, части 5 и 7).
Публичная история не чистится задним числом, а первая локальная сборка несла то,
чему в публичном репозитории не место (выдержки статей, сырые ответы T-Invest,
необезличенный рецепт миров). Поэтому в репозиторий уходит **один свежий корневой
коммит** рабочего дерева, без прежней истории. Push необратим: всё, что попало в
корневой коммит, остаётся публичным.

Команды — из корня рабочей копии, в Git Bash (на Linux питон — `.venv/bin/python`).
Путь к папке передачи в репозиторий не пишется — его спрашивает вторая команда:

```bash
PY=.venv/Scripts/python.exe; export PYTHONIOENCODING=utf-8
read -r -p "папка передачи (вне репозитория): " H
A="$H/private/push-acceptance"          # шаблоны приёмки: в публичный репозиторий не переносятся
ls "$H/private/hygiene-words.txt" "$A"/removed-paths.txt "$A"/absent-patterns.txt "$A"/source-urls.txt "$A"/source-urls.expected.txt
TACT=$(sed -n 's/^TACT_TESTS="\(.*\)"$/\1/p' ops/run.sh); echo "$TACT"
```

**Пока идут шаги 1–5, в этой рабочей копии не запускается ничего другого** — ни
второго прогона pytest, ни сборки: приёмка сверяет состояние ветки и дерева, и
оно не должно меняться под руками. Тесты в рабочую копию не пишут: git в тестах
работает только во временном каталоге прогона и под потолком
(`tests/support_git.py`, `tests/conftest.py`), а второй прогон pytest с тем же
каталогом временных файлов отказывает при старте. Команды этого раздела ходят со
своим каталогом — `--basetemp=var/pytest-push`.

1. **До коммита.** Каждая команда печатает свой итог:
   ```bash
   $PY -m pytest --basetemp=var/pytest-push \
       --deselect tests/test_ops_ci.py::test_the_history_of_the_branch_never_carried_raw_tinvest_answers
   echo "весь набор, кроме теста истории ветки: код $?"             # «N passed, 1 deselected», код 0
   green=0
   for d in 1 7 30 60; do
     FAKE_TODAY=$(date -u -d "+$d days" +%F) $PY -m pytest -m "$TACT" --basetemp=var/pytest-push; rc=$?
     echo "набор сервера на сегодня + $d дн.: код $rc"
     if [ "$rc" -eq 0 ]; then green=$((green + 1)); fi
   done
   echo "ИТОГ: набор сервера зелёный на $green датах из 4"          # 4 из 4
   BANK_HANDOFF_DIR="$H" $PY -m pytest -rs -m archive tests/test_public_hygiene.py --basetemp=var/pytest-push
   ```
   Годный итог — три строки: «весь набор, кроме теста истории ветки: код 0»,
   «ИТОГ: набор сервера зелёный на 4 датах из 4» и «1 passed» сверки с личным
   списком слов. Тест истории
   `tests/test_ops_ci.py::test_the_history_of_the_branch_never_carried_raw_tinvest_answers`
   из первого прогона снят: ветка ещё несёт прежнюю историю, и он зеленеет только
   после шага 3 (его гоняет приёмка шага 4). У сверки с личным списком слов
   `skipped` или `failed` — push не делать (без списка или без папки передачи тест
   краснеет, а не пропускается). Второй ключ `-q` к этим командам не добавлять:
   тихий режим уже задан в `pytest.ini`, а с двумя pytest не печатает итоговую
   строку.
2. **Прежняя история — в локальную ветку**, которая не пушится никогда:
   ```bash
   git branch local-history-2026-10-01 main
   ```
3. **`main` — веткой-сиротой одним коммитом.** После `checkout --orphan` индекс
   ещё несёт дерево прежнего коммита, поэтому он сначала очищается (рабочее
   дерево не трогается; команда годится и для дерева с незакоммиченными
   правками), а затем наполняется явными путями — без `git add -A`:
   ```bash
   git checkout --orphan root-commit
   git read-tree --empty; git ls-files | wc -l                      # индекс пуст: 0
   git add -- .gitattributes .gitignore .github README.md pytest.ini requirements.txt wrangler.toml \
              data docs functions indicators model ops tests web var/.gitkeep
   git status --short | grep -v '^A  '                              # пусто: неотслеживаемого и лишнего нет
   git diff --cached --name-status --diff-filter=AD local-history-2026-10-01   # глазами: что добавлено и убрано против прежней истории
   git -c user.name=ML371KL -c user.email="$(grep -v '^#' .github/commit-emails.allow | head -1)" \
       commit -q -m "Сбер 850: модель справедливой стоимости акции, конвейер и витрина"
   git branch -M main
   ```
   Каждая строка `A` и `D` второй проверки — файл, заведённый или убранный
   сознательно (лист дивидендов с полями ответа T-Invest и выписка его ответа из
   входов листа β обязаны быть среди `D`).
4. **Приёмка по той ссылке, что уйдёт в push** (а не по `--all`: локальная ветка
   законно хранит прежнюю историю):
   ```bash
   git rev-list --count main                                        # 1
   git log main --format='%ae %ce' | sort -u                        # одна строка, оба адреса — из .github/commit-emails.allow
   $PY -m pytest tests/test_ops_ci.py tests/test_public_hygiene.py tests/test_ops_git_sandbox.py --basetemp=var/pytest-push
   echo "история ветки и гигиена дерева: код $?"                    # код 0: в истории ветки нет сырых ответов T-Invest
   BANK_HANDOFF_DIR="$H" $PY -m pytest -rs -m archive tests/test_public_hygiene.py --basetemp=var/pytest-push   # «1 passed»
   git ls-tree -r --name-only main -- $(cat "$A/removed-paths.txt")           # пусто: убранных фикстур в дереве нет
   git grep -n -E -f "$A/absent-patterns.txt" main; echo "код $?"              # пусто, код 1
   git grep -n -E -f "$A/source-urls.txt" main -- ':!data/'; echo "код $?"     # пусто, код 1
   git grep -c -E -f "$A/source-urls.txt" main -- data/ | diff - "$A/source-urls.expected.txt" && echo "ссылки-источники — как ожидалось"
   git rev-list --count main; git status --short | wc -l            # снова 1 и 0: прогоны приёмки не оставили в ветке и в дереве ничего
   ```
   Три проверки удалённого вместо одной: убранные фикстуры — по путям; шаблоны,
   которых в дереве не бывает (посты каналов, имя и суммы другого эмитента), — по
   всему `main`, включая `data/`; адреса двух статей — везде, кроме `data/`, а в
   `data/` — ровно строки-ссылки на источники чисел из файла ожидания. Исключать
   `data/` целиком нельзя: необезличенный рецепт миров лежал именно там.
5. **Push только одной ссылки:**
   ```bash
   git remote add origin https://github.com/ML371KL/temp-zero-inode-850-sber.git
   git push origin main                       # без --all, --mirror и тегов прежней истории
   git ls-remote origin                       # HEAD и refs/heads/main — и только
   ```
6. **Сразу после push** — прогон CI на `main` зелёный; в шаге «Тесты такта — замер
   времени» строка «такт: N с из 300 (цель сервера — 180 с)». Шаг красный (N больше
   300) — снять метку `tact` с самых долгих тестов (список — `--durations` того же
   шага). N больше 180 — предупреждение шага, не отказ: цель сервера сверяется
   замером первых тактов на сервере (раздел 5, шаг 14). Затем правила ветки
   (раздел 5, шаг 4) и установка на сервер (раздел 5).
7. Дальше — обычный порядок (раздел 7): рабочая ветка → CI → fast-forward `main`.
